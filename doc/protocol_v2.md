# aVPN 协议 v2：极小数据帧开销 + 无感知网络切换

目标：把每个数据帧在网络上占用的字节数压到最小；同时让客户端换网（源 IP 或端口变了、
NAT 映射变了）时完全无感知——不重新握手、不中断会话、虚拟地址不变。握手和控制消息
频率很低，允许更大。

---

## 术语与记号（先读）

### 记号约定

- `0x45`：十六进制数（`0x` 是十六进制前缀）。多字节整数一律小端（低位字节写在前面）。
- `0x4x`：高 4 位固定是 4、低 4 位任意，即 `0x40`~`0x4F` 这 16 个值。
- `A(2)`：字段 `A` 占 2 个字节。
- `A || B`：把 `A`、`B` 两段字节首尾接起来。
- `[ A , B ]`：一帧内按 `A`、`B` 的先后顺序拼接各字段，本文用逗号分隔字段顺序。
- `0×8`：8 个取值为 0 的字节。
- `2^32`：2 的 32 次方，即 4294967296。
- `...`：此处省略，细节见相邻说明。
- `O(1)` / `O(n)`：耗时与规模无关 / 耗时随规模 n 线性增长。

### 通用概念

| 术语 | 含义 |
|---|---|
| 明文 / 密文 | 加密前的数据 / 加密后的数据 |
| AEAD | 一种“加密和校验一次做完”的加密方式，本项目用 ChaCha20-Poly1305 |
| 认证标签（tag） | AEAD 在密文末尾附上的一段校验值，接收方靠它判断数据是否被改动或伪造 |
| `tag_len` | 认证标签占几个字节，本文默认 16，也可协商成 12 |
| 密钥 | 加解密用的秘密值，32 字节 |
| 静态密钥 / 临时密钥 | 长期不变、代表客户端身份的一对密钥 / 每次握手现生成、用完即弃的一对密钥 |
| nonce | 每次加密都必须换一个的一次性数字；同一把密钥下 nonce 重复会严重泄漏明文 |
| `K_master` | 握手协商出的会话主密钥，本方案其它密钥都由它派生 |
| HKDF | 一个标准算法：拿主密钥、盐和用途标签算出子密钥 |
| 盐（salt） | 派生密钥时掺进去的附加输入，让同一主密钥能派生出不同子密钥 |
| X25519 / DH | 一种椭圆曲线密钥交换算法，握手时双方各出一对密钥，算出同一个共享秘密 |
| AAD | 只参与校验、不被加密的附带数据 |
| 重放 | 攻击者把抓到的报文原封不动再发一次 |
| 重放窗口 | 接收方记录最近收过哪些序号，据此丢弃重放和过期的报文 |

### 网络概念

| 术语 | 含义 |
|---|---|
| 网关 / 客户端 | 隧道的两端：网关是服务器侧，客户端是用户侧 |
| 帧 | 隧道里一个独立的加密单元，一个 UDP 报文通常正好装一帧 |
| 载荷 | 帧里真正要送的数据，比如一个 IP 包 |
| 帧开销 | 一帧里除载荷之外的字节数，等于帧头加认证标签 |
| 报文 | 一个 UDP 数据报，本文默认走 UDP，一个报文装一帧 |
| MTU | 单个网络报文允许的最大字节数 |
| RTT | 一次网络往返所需的时间 |
| GSO | 内核 / 网卡的一项批量发送优化：把多个等长小帧合并成一次系统调用发出 |
| 端点 | 对端的“IP 地址 + 端口”组合 |
| 上行 / 下行 | 客户端发往网关的方向 / 网关发往客户端的方向 |
| NAT | 网络地址转换：把内网地址映射成公网地址，映射关系随时可能变 |
| 套接字（socket） | 操作系统提供的网络收发接口 |
| 保活 | 一段时间没有数据时双方定期互发一个小包，确认对端还在线，也让 NAT 映射不超时 |
| 混淆 | 把报文伪装成随机数据，让中间人不容易认出这是隧道流量 |

### 本文自定义概念

| 术语 | 含义 |
|---|---|
| 帧头 | 帧最前面的固定 4 字节，明文传输；它的值就是计数器 |
| 计数器 | 帧头里的 32 位数值，每发一帧加一 |
| 次代 | 计数器从 0 数到 2^32 算一个次代；一旦回绕就进入下一个次代并换一把密钥。次代本身不写进报文，收发双方各自推算 |
| 隐式 | 不写进报文，由收发双方各自推算出来 |
| 整帧模式 | 不开纠错时的模式：一帧装一个 IP 包，或装一个容器 |
| 容器 | 把多个 IP 包串在一帧里的格式：标记 + 条目数 + 各条目；用来聚合，也可以选地装进一片 |
| 聚合度 `K` | 一个容器里装了几个 IP 包 |
| 纠错模式 | 开纠错时的模式：一个 IP 包就是一片，另外多带几片冗余片，见 §2.4 |
| 数据片 | 纠错模式里装内容的那种片：一片装一个 IP 包、一个容器，或一条控制消息 |
| 冗余片 | 由数据片算出来、不带内容的那种片，用来把丢掉的片补回来 |
| 补零 | 参与纠错运算时把短的片用 0 补到同一长度；补出来的 0 不进报文 |
| 片长 `S` | 一组各片参与纠错运算时的长度；等于本组最长数据片的长度，只有冗余片按这个长度发送 |
| FEC | 前向纠错：一组里多带几片冗余，丢几片仍能还原 |
| Reed-Solomon | 一种纠错编码，本文用它从数据片算出冗余片，也用它把丢失的片补回来 |
| `T` / `ds` | 一组的总片数 / 其中数据片的片数；剩下 `ps = T − ds` 片是冗余片 |
| 组号 / 片号 | 片属于哪一组 / 是组内第几片。两者都由计数器算出，不写在报文里 |
| 漫游 | 客户端所在网络变了，源 IP 或端口随之改变 |
| `roam_cookie` | 网关在握手中下发的 8 字节随机凭证；客户端换地址后带上它，网关不用逐个会话试解密就能认出是哪个会话 |
| `hint` | 握手时可以附带的一段客户端公钥哈希前缀，让网关一次查表就找到身份，不必逐个试 |
| 回绕 | 计数字段数到最大值后回到 0，本方案在回绕时换密钥 |
| 条目 | 容器里的一段独立数据：要么一个 IP 包，要么一条控制消息 |
| 白名单 | 网关配置里“允许接入的客户端公钥”名单，握手时用它确认来者身份 |

## 1. 目标与安全边界

### 1.1 必须做到

| 编号 | 要求 |
|---|---|
| R1 | 数据帧的帧开销极小：除帧头和认证标签外不多一个字节 |
| R2 | 换网无感知：不重新握手、不中断会话、虚拟地址不变 |
| R3 | 网关查会话表是 O(1)（耗时与会话总数无关） |
| R4 | 报文里不出现明文类型标识：帧的类型、载荷的类型都不明文暴露 |
| R5 | 抗重放，且 nonce 永不重复 |

### 1.2 可以放宽

- 握手可以很大（整个会话只做一次）。
- 控制消息（保活、断开）可以略大（低频）。
- 漫游帧、刚换网时的第一帧可以大（低频事件）。

### 1.3 要防什么

需要防：被动流量分析；注入、篡改、重放；对握手和漫游入口的洪水攻击；漫游被第三方
抢认领。不需要防：端点本身已被攻陷；依赖时钟同步的攻击（本方案不使用时间）。

## 2. 报文格式

`tag_len` 默认 16。

### 2.1 一共哪几类报文

| 类别 | 结构 | 用途 |
|---|---|---|
| 握手报文 | 见 §2.2 | 建立会话，只在开始时做一次 |
| 数据帧（整帧模式） | 帧头(4) + 密文 | 不开纠错时用：一帧装一个 IP 包，或装一个容器，见 §2.3 |
| 数据片帧（纠错模式） | 帧头(4) + 密文 | 开纠错时用：一片装一个 IP 包、一个容器（多个包聚合，见 §2.4）、一条压缩载荷，或一条控制消息，见 §2.4 |
| 冗余帧（纠错模式） | 帧头(4) + 密文 | 开纠错时用：由数据片算出来的冗余片，见 §2.4 |
| 漫游帧 | cookie(8) + 帧头(4) + 密文 | 换网或保活时用，见 §2.5 |
| 混淆层 | 见 §2.6 | 可选，套在数据帧外面（握手报文和带 cookie 的漫游帧不套） |

这几种帧只有两处不同：漫游帧最前面多 8 字节 `cookie`，明文里装的东西不一样，其余
完全一样。

上面写的都是 UDP 的线格式：一个数据报就是一帧。走 TCP 时每一帧还要多套一层 2 字节
长度前缀，见 §2.8。

把密文解开后，看明文的第一个字节就知道这一帧装的是什么：

| 明文第一个字节 | 装的是什么 | 说明 |
|---|---|---|
| `0x4x` 或 `0x6x` | IP 包 | IPv4 / IPv6 裸包，直接投递 |
| `0x00` | 容器 | 一帧装了多个条目，结构见下 |
| `0x01` | 压缩载荷 | 压后长度(2) + 压后数据；解压出来是一个 IP 包，只在开了压缩时出现 |
| 其它 | 控制消息 | 消息码(1) + 长度(2) + 内容 |

**为什么明文的第一个字节可以当类型用**

IP 协议规定报文的第一个字节高 4 位就是版本号：

```
IPv4 首字节 = [版本 = 4][IHL]            = 0100 xxxx = 0x4x
IPv6 首字节 = [版本 = 6][流量类别高 4 位] = 0110 xxxx = 0x6x
```

`IHL` 是 IPv4 的头部长度（以 4 字节为单位，5 表示 20 字节头），流量类别是 IPv6 的
一个字段，但这两个都不影响高 4 位。所以 `0x4x` / `0x6x` 只能出现在 IP 报文开头，
相当于 IP 包自带的“签名”。接收方只要看高 4 位是不是 4 或 6 就能判断。

- `0x00`：IP 版本 0 不存在，永远不会和 IP 签名冲突，所以留作容器的标记。
- `0x01`：留给压缩载荷，格式同样带 2 字节长度，用来在纠错模式里剥掉补零。
- 其它取值：既不是 IP 签名也不是容器标记，留给隧道自己的控制消息，第一个字节是消息码。

控制消息的消息码定义如下：

| 消息码 | 消息 |
|---|---|
| `0x02` | 保活请求 |
| `0x03` | 保活回复 |
| `0x04` | 主动断开 |
| `0x05` | 漫游凭证更新：内容就是 8 字节新凭证（见 §4.3） |

其它消息码保留，暂未使用。

约束：自定义消息码不能落在 `0x40`~`0x4F`、`0x60`~`0x6F`，否则会被当成 IP 包；
`0x00` 和 `0x01` 不能作消息码，前者留给容器标记，后者留给压缩载荷。

有了这条规则，数据帧不必再花一个字节去写“我装的是什么”；只有低频的控制消息才需要
一个消息码。控制消息自带 2 字节长度，是因为开纠错时它可能作为一片被解出来，那时没有
帧长可看（见 §2.4）。

**容器的结构**

容器用来把多个 IP 包装进一帧（聚合）：不开纠错时它让一帧一次搬走很多包；开纠错时它
是可选的，用来把几个包塞进同一片（见 §2.4）。

```
[ 0x00 , 条目数(1) , 条目1 , 条目2 , ... ]
```

- 条目数占 1 字节（最多 255 个条目），读完这么多个条目就结束，后面的填充字节
  一律忽略。
- 每个条目的判法同上：下一个字节是 `0x4x` / `0x6x` 就按 IP 包处理，长度从 IP 头
  自带的总长字段读出——IPv4 取包头第 3~4 字节的总长字段，IPv6 取 payload-length
  字段（第 5~6 字节）再加 40——所以包前不需要任何长度字段；否则是控制条目，格式为
  `[ 消息码(1) , 长度(2) , 内容 ]`，用长度跳过。
- **解析时逐个条目校验**（容器内容来自对端，按不可信数据处理）：
  - 每读一个条目先看剩余字节：剩余为 0 就结束，不足 `条目数` 个条目就整帧丢弃。
  - 读到 IP 包时，设从 IP 头算出的长度为 `L`：IPv4 要求 `20 ≤ L ≤ 剩余字节数`，
    IPv6 要求 `40 ≤ L ≤ 剩余字节数`，不满足就整帧丢弃。
  - 读到控制条目时，要求剩余字节数 ≥ 3，且 `3 + 长度 ≤ 剩余字节数`，否则整帧丢弃。
  - 任何一条不满足都整帧丢弃，不做“尽力解析”，避免畸形长度把解析带出界。

举例：

| 明文第一个字节 | 判定 | 说明 |
|---|---|---|
| `0x45` | IPv4 包 | 版本 4、头部 20 字节，最常见 |
| `0x46` | IPv4 包 | 版本 4、头部 24 字节（带选项） |
| `0x60` | IPv6 包 | 版本 6、流量类别高 4 位为 0，最常见 |
| `0x6B` | IPv6 包 | 版本 6、流量类别高 4 位为 B |
| `0x00` | 容器 | 后接条目数与各条目 |
| `0x02` | 控制消息 | 保活请求（低频） |

> 有两层要分清：帧头是密文外面的 4 字节，位置固定在帧的最前面，加密不覆盖它，
> 接收方解密之前就能读到（用来推导 nonce、做去重、算纠错的组号和片号）；而密文
> 里面没有任何额外字段，明文的第一个字节就是载荷自己的第一个字节。

### 2.2 握手报文（允许大）

```
C → S: [ hint(8) , 随机数(12) , AEAD(K_temp, 随机数, 明文) ]
       明文 = [ 版本(2) , 临时公钥(32) , 时间戳(8) , 客户端标识(16) ,
              期望虚拟地址(4) , 参数长度(2) , 参数 ]
S → C: [ 随机数(12) , AEAD(K_resp, 随机数, 明文) ]
       明文 = [ 临时公钥(32) , 参数长度(2) , 参数 ]
```

`C → S` 表示客户端发给网关，`S → C` 表示网关发给客户端。`AEAD(K, nonce, 内容)` 表示
用密钥 `K` 和 `nonce` 对内容做认证加密；每条握手报文最前面那 12 字节随机数，就是这条
报文自己现取的 nonce。

`hint` 写在密文外面（请求报文最前面 8 字节），因为网关要先认出“这是哪个客户端”，
才知道拿哪把静态密钥去解密；放进密文里就成了死循环。不用 `hint` 时填 8 个 0。

两条握手报文的认证标签固定 16 字节：`tag_len` 本身就在握手时才谈定，握手报文只好先用
固定值；数据帧才按谈定的 `tag_len` 走。

客户端发出请求后，5 秒内没等到回复就重发一次（时间戳、随机数都重新生成，参数照旧），
最多重发 5 次；再没有回复就放弃这次会话，等 3 秒重建会话、重新握手。TCP 和 UDP 都是
这套重发逻辑：连接被中间设备静默掐断、对端没收到请求时，靠它及时发现，不必等系统
层面的超时。

各字段含义：

| 字段 | 字节 | 含义 |
|---|---|---|
| 版本 | 2 | 协议版本，供收发双方协商一致 |
| 临时公钥 | 32 | 本次握手现生成的公钥，用来算出会话密钥 |
| 时间戳 | 8 | 发送时刻的毫秒数，供防重放 |
| 客户端标识 | 16 | 客户端名字，只写日志，不参与密钥和路由 |
| 期望虚拟地址 | 4 | 客户端想用的虚拟地址，0 表示由网关分配 |
| `hint` | 8 | 写在密文外面；客户端静态公钥的哈希前缀，供网关一次查表找到白名单项；8 个 0 表示不带（网关就逐个白名单项试，见 §8.1） |
| 参数长度 / 参数 | 2 / 变长 | 参数占多少字节，以及参数的内容 |

参数把本会话要用到的取值集中在一起，在握手时一次谈定（握手允许大，不必省字节）。
每一条参数的写法都是 `[ 参数号(1) , 长度(2) , 内容 ]`，`长度` 只算内容那一段；把要谈的
参数按参数号从小到大首尾接起来，就是报文里那一段“参数”。接收时按参数号解析，碰到不认识
的参数号就按 `长度` 跳过去；同一条参数不许出现两次，重复出现就判握手失败。

| 参数号 | 参数 | 内容 |
|---|---|---|
| `0x01` | 版本 | 2 字节；回复报文里用它告诉客户端最终用哪个版本（请求报文里的版本在报文开头的字段里） |
| `0x02` | `tag_len` | 1 字节，16 或 12 |
| `0x03` | 纠错 `T` / `ds` | 各 1 字节；`T = 1` 表示不开纠错（此时 `ds` 为 1），开纠错时 `T` 取 2、4、8、16，`2 ≤ ds ≤ T − 1` |
| `0x04` | 保活间隔 | 2 字节，秒 |
| `0x05` | 组放弃超时 | 2 字节，毫秒，见 §2.4 |
| `0x06` | 组缓存时限 | 2 字节，毫秒，见 §2.4 |
| `0x07` | 提前关组 | 2 字节，0 表示关闭，否则是毫秒 |
| `0x08` | `mtu` | 2 字节，客户端虚拟网卡的 MTU |
| `0x09` | 虚拟地址 / 前缀 | 4 字节虚拟地址 + 1 字节子网前缀长度 |
| `0x0A` | `v6` | 1 字节前缀长度 + 16 字节网络地址 |
| `0x0B` | 路由 | 条目数(1) + 各条目 `[ 长度(1) , 路由文本 ]` |
| `0x0C` | 压缩 | 1 字节，0 表示不压缩，1 表示 deflate（原始 deflate 流，不带 zlib 头），2 表示 lz4（块格式）；两端配成同一个算法才生效，其它值保留 |
| `0x0D` | 混淆 | 1 字节，0 / 1 |
| `0x0E` | `roam_cookie` | 8 字节漫游凭证，见 §4 |
| `0x0F` | `cookie_beacon_K` | 2 字节，每多少个数据帧顺带一次 cookie，0 表示关闭 |
| `0x10` | 传输类型 | 1 字节，0 = UDP，1 = TCP |
| `0x11` | 推送 DNS | 4 字节虚拟网络内可用的 DNS 地址，0 表示不推 |
| `0x12` | 全局出口 | 1 字节，1 表示默认把全部流量都走这条隧道，0 表示只走推送的路由 |
| `0x13` | 混淆密钥指纹 | 4 字节，混淆密钥串的指纹；客户端用它告诉网关自己配的密钥，网关对不上就拒绝这次握手 |

两个方向用的是同一套参数：客户端在请求里放自己希望的取值（可以只放一部分），网关在回复
里放最终定下来的取值，也就是这个会话真正要用的值；客户端没提的，网关按默认值（见 §8.1）
下发。

**握手这两把密钥怎么来**

`K_temp` 和 `K_resp` 都由同一个共享秘密派生，这个秘密用双方**静态密钥**算：客户端
手里有自己的静态私钥和网关的静态公钥；网关手里有自己的静态私钥，再按 `hint`（或逐个
白名单项试）找到客户端的静态公钥。两把密钥只靠用途标签区分方向：

```
共享秘密 = DH(客户端静态私钥 , 网关静态公钥)      // 网关侧用对称的算法算同一个值
K_temp   = HKDF-SHA256(ikm = 共享秘密 , info = "avpn-hs-temp-v2" , L = 32)
K_resp   = HKDF-SHA256(ikm = 共享秘密 , info = "avpn-hs-resp-v2" , L = 32)
```

- 这两把密钥只由双方静态密钥决定，同一个客户端的每次会话都一样；它们只保护握手这一
  小段。真正给数据用的是下面四次 X25519 派生出的主密钥，每次会话都不同；握手里的
  临时公钥一直待在密文里，不会明文出现在网络上。
- 握手报文带时间戳，网关按对端记录最近接受的时间戳，拒绝回退或重复的请求。
- 回复报文里也带着网关自己的临时公钥，但它只参与下面会话主密钥的派生，不参与这两把
  密钥：不然客户端在解密之前拿不到这个公钥，绕不开自己。

会话主密钥由四次 X25519（4-DH）派生。双方用各自的静态密钥与本次握手的临时密钥算出
四个共享秘密：静态×静态、静态×临时、临时×静态、临时×临时；把后三个按字典序排序后
拼起来作为输入，把“静态×静态”作为盐，经 HKDF-SHA256 算出 32 字节的主密钥。按字典序
排序是为了让两端视角互换（“我的静态”对“对端的静态”）时仍能算出同一个值。

### 2.3 数据帧（整帧模式，`T = 1`）

```
[ 帧头(4) , AEAD(K_e, nonce = 帧头 || 0×8, 明文) ]
```

- 帧头是一个 32 位计数器，每发一帧加一；数到 2^32 回绕时换一把密钥（见 §3）。
- 解密后没有任何协议字段，明文第一个字节按 §2.1 的规则判定内容。
- 帧开销 = 4 + `tag_len`，即 **20 字节**（`tag_len = 16`）或 **16 字节**
  （`tag_len = 12`）。

### 2.4 数据片与冗余片（纠错模式，`T > 1`）

开纠错时，**一个包就是一片**：从虚拟网卡读到包就立刻发出去，同时留一份；凑够 `ds`
片就把 `ps` 片冗余片算出来发出去，这一组结束。补零只用于纠错运算，不进报文。几个包
聚成一个容器时，一个容器算一片；控制消息也一样，各占一片。

```
数据片帧： [ 帧头(4) , AEAD(K_e, nonce = 帧头 || 0×8, 明文) ]
           明文 = IP 包（首字节 0x4x / 0x6x）
                 或 容器 [ 0x00 , 条目数(1) , 各条目 ]（几个包聚成一片，见 §2.1）
                 或 压缩载荷 [ 标记(1) , 压后长度(2) , 压后数据 ]（见 §2.7）
                 或 控制消息 [ 消息码(1) , 长度(2) , 内容 ]
冗余帧：   [ 帧头(4) , AEAD(K_e, nonce = 帧头 || 0×8, 冗余片) ]
           冗余片 = Reed-Solomon 算出的 S 字节
```

- 片长 `S` = 本组数据片里最长的那一片的长度。数据片按自己的长度发，不补零；冗余片
  就是 `S` 字节。
- 接收端从冗余帧的帧长反推 `S`（`S` = 帧长 − 4 − `tag_len`），报文里不需要长度字段。
- 帧长本身就受 AEAD 保护：密文长度一改，认证标签必然验不过，所以可以放心拿帧长当
  长度用。
- 控制消息为什么带长度字段：解出来的片只知道自己被补到 `S` 长，得靠它才能剥掉补零；
  IP 包自带总长字段，不需要。
- 片长上限：`S` ≤ 线缆 MTU − 20 − 8 − 4 − `tag_len`（线缆 MTU 1500、`tag_len` 16 时
  是 1452；20 和 8 是外层 IP 头与 UDP 头），所以内层虚拟网卡的 MTU 也按它配，保证
  一个包放得进一片。开混淆时还要再减去混淆层的开销（见 §2.6）。

**分组**

- 帧头就是一个 32 位计数器，每发一帧加一；组号 = 计数器 ÷ `T`，片号 = 计数器 mod `T`。
- 片号 `0 ~ ds-1` 是数据片，片号 `ds ~ T-1` 是冗余片。
- 每个会话同时只有一个没结束的组：包来了就占下一个数据片号（计数器跟着加），凑满
  `ds` 片就把冗余片发出去，再开新组（新组的基地址是 `T` 的下一个整数倍）。
- `T` 只取 2、4、8、16（都能整除 2^32），这样一组不会跨次代；用别的取值时，每个
  次代的最后一组会分属两把密钥，永远凑不齐。
- 组的身份 = `次代 × (2^32 ÷ T) + 组号`（次代取接收端解密时确定的那个）。它在一个组
  可能存活的时间（最多几秒）内绝不会重复，不会出现两组片被拼成一组。

**发送端做什么**

1. 读到一个包（或一条控制消息）→ 立刻加密发出，计数器 = 本组基地址 + 已经用掉的
   数据片数。
2. 同时把这份明文留一份，最多留 `ds` 片。
3. 数据片数到 `ds` → 取 `S` = 最长片的长度 → 每片补零到 `S` → Reed-Solomon 算出
   `ps` 片 → 立刻发出（计数器 = 基地址 + `ds` ~ 基地址 + `T` − 1）→ 清掉留的那份，
   开新组。
4. 一组一直凑不满、又超过 `T_group`（默认 1 秒）没有新包 → 放弃这一组：不发冗余片、
   清掉留的那份。下一个包开新组，计数器直接跳到 `T` 的下一个整数倍。

**接收端做什么**

1. 解帧，按计数器算出组号、片号。
2. 数据片（片号 < `ds`）：解出的明文**立刻投递**，不用等整组；同时在本组留一份，后面
   可能要用它解别的片。
3. 冗余片（片号 ≥ `ds`）：留一份，并从帧长得到 `S`。
4. 够条件就解码：已知的片（收到的 + 确定是全零的）不少于 `ds`，而且缺的片不超过
   `ps` → 解出缺的片再投递；解完按容器规则 / IP 总长 / 控制消息长度剥掉补零，并核对
   尾部补零全是 0。
5. 该扔就扔：数据片已经收全 → 直接丢留的那份（根本用不着解码）；一组放太久（超过
   `T_group_recv`，默认 2 秒）→ 丢留的那份。扔掉的只是“补丢包”的机会，已经投递的
   数据不受影响。

**校验规则**（内容来自对端，按不可信数据处理）

- 拿到冗余片知道 `S` 之后，回头校验已经收到的数据片：长度不能超过 `S`；同组冗余片
  推出的 `S` 必须一致。不一致就丢掉整组。
- 解出来的片要和收到的片一样校验：IP 包要满足“IP 总长 ≤ `S` 且尾部补零全是 0”，
  容器要能按条目规则逐个解析完，控制消息要满足长度字段对得上。
- 任一条不满足，只丢这一片，不投递，不影响别的片。
- 片都过了 AEAD 认证，伪造不了；这些检查是防实现出错和对端异常。

**什么时候这套纠错真有用**

- 冗余片要等第 `ds` 个包到齐才算得出来，所以“一组凑齐要多久 = `ds` ÷ 包速率”。
  丢的包要在对端重传之前把片补回来才有意义，也就是要在一个 RTT 内到齐。
- 按 `ds` = 12、RTT 20 毫秒算，包速率大约 600 包/秒以上才有用；更慢的流量，冗余片
  到得比重传还晚，等于白花带宽（好在流量本身小，代价也小）。
- 想按链路丢包调整冗余比例，只能在新建会话（重新握手）时改 `T` 和 `ds`。
- 补得回来的是零散丢掉的片。一组里连着丢超过 `ps` 片，这一组就补不回来了，所以
  丢包成串（比如发送端出口排队溢出、一次丢掉一整批）的地方，加冗余也救不回来，
  得先把发送端的排队控制住。

**两条增强**

- **提前关组**（默认关闭）：一连串包之后长时间没有新包（突发流），这一组可能永远凑
  不满，冗余永远发不出去。这时可以在超过 `T_flush` 后直接关组，把还缺的数据片当成
  全零，并把冗余片的明文改成 `[ 实际数据片数(1) , 冗余片(S) ]`，接收端据此区分“本来
  就是全零的片”和“丢掉的片”。代价是每片冗余多 1 字节，低速率时一组往往只有一两个
  真包，冗余会按片长等比放大。
- **机会性聚合**（当前实现已启用）：从虚拟网卡一次读到的往往不止一个包，把能放进同一
  片的几个包按 §2.1 的容器格式塞进一片，片长按容器长度算，补零照样不发送；解出来的片
  按容器规则解析（尾部填充本来就忽略）。好处是把每包 20 字节的封装摊薄。前提是不为
  攒包等待：只装手里已经拿到的包，不然攒包延迟又回来了；整帧模式同样适用（一帧装一个
  容器）。

### 2.5 漫游帧

```
[ cookie(8) , 帧头(4) , AEAD(K_e, nonce = 帧头 || 0×8, [消息码(1) , 内容]) ]
AAD = cookie
```

漫游帧就是“多带 8 字节 cookie 的数据帧”，用在换网和保活两种场合。

- `cookie`：8 字节漫游凭证，握手时由网关下发。放在最前面，网关**在解密之前**就能
  判断这是哪个会话，不用逐个会话试解密。
- `AAD = cookie`：cookie 作为 AEAD 的附加校验数据一起参与校验，第三方既无法篡改
  cookie，也无法伪造这类帧。
- 密文里是一条控制消息（保活、空载荷等），格式同 §2.1。
- 漫游帧和其他帧共用同一个计数器，同样每发一帧加一，因此不会产生 nonce 重复。开纠错
  时它照样占一个片号，`cookie` 不算片的内容，片长按密文长度算。
- 只在换网或保活时发送，平时的数据帧不带 cookie。
- 网关重新绑定（客户端换网）之后会换一把新凭证，并立刻用控制消息 `0x05` 告诉客户端
  （见 §4.3）。
- 只在 UDP 下出现：TCP 的连接本身就认得出是哪个会话，不需要 cookie，握手参数
  `0x0E` / `0x0F` 在 TCP 会话里都是 0（见 §2.2、§2.8）。

### 2.6 混淆层（可选）

混淆层套在**数据帧**外面，给每个包加一段随机垃圾。帧头被推到报文中间，包长也不再等于
“载荷 + 固定开销”，旁观者不容易从“包有多大、包长怎么分布、开头几个字节长什么样”
认出这是隧道流量。

```
[ 随机数(4) , 长度(2) , 垃圾(16~64) , 原来的帧 ]
```

- `随机数`：每包现取的 4 字节随机数，两端用它算出同一个掩码。
- `长度`：垃圾字节数按 16 位掩码异或后的值；掩码由两端配置的同一个密钥串和`随机数`
  一起算出（双方都配了同一个密钥串才有掩码），所以线上看不到垃圾到底多长。
- 垃圾：16~64 个随机字节。到底取多长**只看帧长**，不随机：同样长的帧套出来还是
  同样长（见下面的取舍）。
- 掩码和`随机数`绑在一起：第三方改了这两处任何一处，算出来的垃圾长度就变了，帧的
  起点跟着错位；帧本身还有认证标签，解不开就丢。

几点约定：

- 只在**会话建立之后**的数据帧上套。握手报文不套，因为“开不开混淆”正是握手谈定的
  （参数 `0x0D`）；两端都配了密钥串、且密钥串一致才谈得成，否则握手直接失败。
- **带漫游凭证的帧不套**：网关要先看到最前面那 8 字节凭证，才能一步认出是哪个会话。
  这类帧只在换网和按 `cookie_beacon_K` 顺带时出现，频率低。
- TCP 传输时，混淆层套在长度前缀里面，也就是 `[ 长度(2) , 混淆层 , 帧 ]`，接收方还得
  靠长度前缀切记录（见 §2.8）。
- 开启后每包多 22~70 字节（4 字节`随机数` + 2 字节`长度` + 16~64 字节垃圾），还要从
  片长上限里再让出 70 字节给最坏情况，内层 MTU 于是跟着变小（默认 1450 降到 1382）。
  这是开混淆的主要代价，和“极小开销”的目标互相冲突，由部署方自行选择，默认关闭。
- 垃圾长度为什么不做成随机的：内核的合并优化（收方向的 GRO、发方向的 GSO）只认
  **等长**的相邻报文。帧长本来就不是秘密（就在报文长度里），把长度再随机化只会打掉
  这个优化，实测吞吐要掉三成，而旁观者能多知道的东西几乎没有。

### 2.7 压缩

压缩是可选能力，两端握手时用参数 `0x0C` 谈定（见 §2.2），只有两端配成同一个算法才生效，
默认不压缩。当前实现了两种：

| 参数值 | 算法 | 压后数据 | 取舍 |
|---|---|---|---|
| 1 | deflate | 原始 deflate 流（不带 zlib 头） | 压得更狠，但每包都要跑一遍 zlib，吃 CPU |
| 2 | lz4 | lz4 块格式的压后数据 | 压得浅一些，速度快得多 |

```
压缩载荷：[ 标记(1) = 0x01 , 压后长度(2, 小端) , 压后数据 ]
```

标记 `0x01` 只说“这包是压过的”，具体用哪种算法看这个会话谈成的结果：两端谈的不是同一个
算法就谈不成压缩（参数 `0x0C` 只有两边一样才生效），所以不会出现一边按 deflate 解、
一边按 lz4 压的情况。会话中途不换算法。

- 只压 IP 包。容器、控制消息、漫游帧里的保活消息都不压，压缩不上就不压。
- 压后数据加 3 字节条目头之后，必须比原包小才发压缩载荷；否则还是发原始 IP 包。
  所以包本来压不动时，一个字节都不会多花。
- 压不压是发送方自己的取舍，接收方不需要知道原因：太短的包、一眼看上去压不动的包
  （已经加密的载荷、压过的媒体流这类字节几乎不重复的数据）发送方直接跳过，省下压缩
  本身的 CPU。压缩是拿 CPU 换带宽，链路上不缺带宽时可以把压缩关掉。
- 接收方解密后先看首字节：是 `0x01` 就按上面的格式取出压后数据解压，解出来的就是一个
  IP 包，直接投递；长度字段用来在纠错模式里剥掉补零。
- 解压结果最多允许一个满长包（`mtu` 大小），超了就整片丢弃，防止对端用“解压炸弹”
  撑爆内存。长度字段越界、数据解不开，同样丢弃。

### 2.8 TCP 传输时的封装

TCP 是字节流，没有“一个报文就是一个包”的分界，所以走 TCP 时每一帧前面固定加 2 字节
长度前缀，接收方靠它把字节流切成一帧一帧：

```
[ 长度(2, 大端) , 帧 ]
```

- `长度` = 后面这一帧的字节数（不含这 2 字节自己），上限 65535。握手报文和数据帧都带
  这个前缀；混淆层算在帧里面，也就是 `[ 长度(2) , 混淆层 , 帧内容 ]`（见 §2.6）。
- 接收方按前缀切记录：先凑够 2 字节读长度，再凑够这么多字节取出一帧；多出来的字节
  留给下一帧。TCP 会把多次发送合并、也会把一次发送拆开投递，所以不能假设“读一次
  正好是一帧”。
- 长度是 0 或超过上限：这一路字节流已经不能按帧对齐了，丢掉当前缓冲重新找帧边界；
  实际运行中这类连接一般已经坏了，靠保活和断开超时收尾。
- TCP 下没有漫游帧：换网认会话靠的就是连接本身——一个连接一条隧道，网关接受连接后
  先握手再收数据，不看源 IP、源端口（见 §4）。连接一断就是这条隧道结束，重连后重新
  握手、重新分配虚拟地址。
- 每帧比 UDP 多 2 字节长度前缀，其余（帧头、加密、纠错、压缩、混淆的格式）完全一样。
- TCP 上来回都是可靠的，纠错补出来的冗余片没有用武之地，只是白占带宽、多排队，所以
  TCP 会话一律按整帧模式（`T = 1`）跑。

## 3. 帧头、密钥、nonce、次代

### 3.1 帧头的含义

- **整帧模式（`T = 1`）**：帧头就是 32 位计数器。
- **纠错模式（`T > 1`）**：帧头同样是 32 位计数器（每发一片加一），组号和片号由它
  算出来：组号 = 计数器 ÷ `T`，片号 = 计数器 mod `T`；片号 `0 ~ ds-1` 是数据片，
  片号 `ds ~ T-1` 是冗余片。

两种模式的数据帧线开销一样，都是 4 + `tag_len` 字节。

### 3.2 密钥与 nonce

```
K_e   = HKDF-SHA256(ikm = K_master, salt = e(8, 小端), info = "avpn-datakey-v2" || dir, L = 32)
nonce = 计数器(4) || 0×8          // 共 12 字节
```

- `K_e`：第 `e` 个次代使用的对称密钥，32 字节。
- HKDF 的四个参数：`ikm` 是输入密钥（这里就是主密钥 `K_master`）；`salt` 是盐
  （这里填次代编号 `e`，8 字节小端）；`info` 是用途标签；`L` 是输出长度。同样的输入
  一定算出同样的密钥。
- `dir` 是方向标签，取 `c2s`（客户端 → 网关）或 `s2c`（网关 → 客户端），
  让两个方向用不同的密钥。
- 主密钥 `K_master` 由 4-DH（四次 X25519）派生，见 §2.2。
- **nonce 不会重复**：同一个次代内计数器每帧都不同，所以 `K_e` 和 nonce 的组合不会
  撞车；跨次代换了密钥，计数器就算回到相同的值也没有影响。
- 发送端有一条硬性要求：**计数器一回绕，必须先进入下一个次代并换好密钥，再继续发送。**
  同一把密钥下计数器绝不重复，这是 nonce 不重复的唯一依靠；实现时必须显式检查这一点，
  不允许回绕后继续用旧密钥发送。
- 每个次代的密钥都由主密钥**直接算出**（不是逐次代链式推的），所以接收方可以 O(1)
  跳到任意一个次代。

### 3.3 接收端怎么确定用哪把密钥

次代不写在报文里，接收端按下面的规则推算。它记两个值：`e_last`（最近一次解密成功
时所在的次代）和 `h_last`（那个次代里见过的最大计数器值）。收到计数器值为 `x` 的
帧时：

- 如果 `x > h_last`，先按还是第 `e_last` 个次代试；否则按第 `e_last + 1` 个次代试。
- 如果一次解密失败，就换另一个次代再试一次；两次都解不开、又还有更早的次代时，再往前
  一个次代试一次。往前试这最后一次是为“正好跨次代、又晚到的旧帧”兜底：那种帧的计数器
  比 `h_last` 大，只看前面两条会把它漏掉（代价只是多试一次解密，AEAD 不通过就是错帧）。
- 解密成功的那个次代就是这一帧真实的次代（密钥错了 AEAD 一定通不过）。

一个次代是 2^32 帧，在 100 Mbps 上约 5.6 天、10 Gbps 上约 80 分钟。只有正好跨次代、且
报文乱序时才会用到第二次尝试，所以这条规则在实际网络上不会失效。

### 3.4 防重放与分组身份

把“次代”和“计数器”合成一个单调递增的全局序号 `g`：

```
g = 次代 × 2^32 + 计数器
```

接收方维护一个滑动窗口：用一串标记记住最近一段序号里哪些已经收到过，只接收窗口内
没出现过的 `g`，重放或过期的直接丢弃；因为 `g` 只增不减，不存在回绕造成的歧义。

纠错模式里组的身份也由 `g` 决定：组身份 = `g ÷ T`，由接收端在解密成功（次代已确定）
之后算出来。因为 `g` 在 2^64 帧内不会重复，而一个组最多存活几秒，两个组不可能被当成
同一个。

## 4. 换网不掉线

这一章讲的是 UDP 传输：UDP 没有连接，网关靠报文本身（cookie 或源地址）认会话，所以
换网后只要让网关认出新地址就行，会话内容一点都不用重建。TCP 传输没有这一套：连接绑在
当前地址上，客户端换网（或 NAT 映射变了）会把连接断掉，客户端重连后重新握手，虚拟
地址、密钥跟着重新协商（客户端会照旧申请原来想要的虚拟地址）。

### 4.1 客户端能察觉的换网（Wi-Fi → 移动网络）

1. 客户端的网络监视器发现本地出口地址变了。
2. 立即在新套接字上发一个漫游帧（`cookie(8)` 加一条保活 / 空载荷消息）。
3. 网关收到来自陌生端点的报文，用 cookie 查表命中，把这个会话的远端端点改成新地址
   （O(1)），换一把新漫游凭证并用控制消息 `0x05` 告诉客户端，然后正常处理，并把回包
   发到新地址。
4. 会话、虚拟地址、密钥、次代全部保留，期间最多丢一个 RTT 的包。

### 4.2 客户端察觉不到的换网（NAT 悄悄改了映射）

- 保活帧一律带 cookie（频率低，开销可忽略）。
- 再让数据帧偶尔也带上 cookie：每 `cookie_beacon_K` 个数据帧顺带一次，使恢复时间
  不超过 `min(保活间隔, K 帧的时长)`。
- 如果客户端“一直在发但超过 `T_no_rx` 没收到任何下行”，立即补发漫游帧。

### 4.3 防止别人抢认领

- cookie 写进 AEAD 的 AAD，第三方无法伪造或篡改漫游帧。
- 重放用过的漫游帧会被重放窗口拒绝（`g` 已经用掉）。
- 已知的边界情况：攻击者若**抢在客户端之前**转发截获的漫游帧，可能抢先绑定。缓解
  办法是每次重新绑定之后都换一把新凭证（见 §4.1）：攻击者手里那把只在重叠期（10 秒）
  内还能用，之后作废；客户端发现下行中断也会补发漫游帧，重新抢回绑定。在 UDP 没有
  源地址绑定的前提下，这个竞态无法彻底消除。

## 5. 安全性小结

| 项目 | 结论 |
|---|---|
| nonce 重复 | 不可能（见 §3.2），而且不需要重新握手换钥 |
| 计数器回绕 | 回绕即换钥，一把密钥只会用 2^32 个计数器值 |
| 重放 | 用 64 位全局序号加滑动窗口，跨次代连续 |
| 类型泄露 | 帧的类型在密文里，靠 IP 版本号或容器标记判别，明文探测不到 |
| 补零与解码 | 补零由接收端按已知长度自己补，不进报文；解出来的片按和收到的片完全一样的规则校验 |
| 陌生端点洪水 | cookie 查表是 O(1) 且很便宜，没命中才进入握手流程，并按源 IP 限速 |
| 握手洪水 | 白名单试解密按源 IP 限速；可选 `hint` 转成 O(1) |
| 标签截断（`tag_len = 12`） | 每次伪造成功概率 2^-96，可接受；默认仍是 16 |

## 6. 帧开销

下表两列分别是 `tag_len = 16` 和 `tag_len = 12` 的情况（单位：字节）；`n` 是控制
消息内容的长度。

| 场景 | `tag_len = 16` | `tag_len = 12` |
|---|---|---|
| 整帧模式：单包一帧 | 20 | 16 |
| 整帧模式：聚合 K = 10（每包平均） | 2.2 | 1.8 |
| 整帧模式：聚合 K = 32（每包平均） | 0.69 | 0.56 |
| 纠错模式：每包平均（`T` = 16、`ds` = 12） | 26.7 | 21.3 |
| 纠错模式：冗余片（每片） | 20 + `S` | 16 + `S` |
| 控制消息帧（另算消息码 1 字节、长度 2 字节） | 23 + n | 19 + n |
| 漫游 / 保活帧（含 cookie，低频） | 31 + n | 27 + n |
| 开启混淆 | 每包再加 22~70，内层 MTU 降 70（见 §2.6） | 同 |
| 走 TCP 传输 | 上表每帧再加 2（长度前缀，见 §2.8） | 同 |

- 纠错模式每包的封装 = 20 × `T` ÷ `ds`，等于把 `ps ÷ ds` 的冗余名额摊到每个包上，
  和包长无关。
- 启用压缩时，压得动的 IP 包换成压缩载荷：帧开销是 20 + 3 字节，但载荷本身变小，
  整体通常更省；压不动的包按原样发，开销和上面一样，一个字节都不多花（见 §2.7）。
- 按 1400 字节载荷折算，整帧模式单包一帧的帧开销占比约 1.41%（`tag_len = 16`）或
  1.13%（`tag_len = 12`）。

纠错模式的实际放大（发出去的字节 ÷ 载荷字节，`T` = 16、`ds` = 12、`tag_len` = 16）：

| 载荷 | 线上字节 | 放大 |
|---|---|---|
| 12 个 1378 字节的包 | 22368 | 1.35× |
| 12 个 40 字节的包 | 960 | 2.00× |
| 6 个 1378 字节 + 6 个 40 字节的包 | 14340 | 1.69× |

冗余片按“本组最长的那一片”定价，所以包长混杂时，短包也要按长包的尺寸分摊冗余；小包
多的流量用整帧模式加聚合（一帧装很多包）更划算。

## 7. 帧头为什么是 4 字节

帧头宽度决定两件事：一个次代有多长，以及接收端最多能容忍多久“对不上”。

- 一个次代的帧数 = 2^(帧头位数)，4 字节就是 2^32 帧。
- 换算成时间，按一帧 1400 字节估：

| 峰值速率（单会话） | 一个次代的时长 |
|---|---|
| 100 Mbps | 5.6 天 |
| 1 Gbps | 13 小时 |
| 10 Gbps | 80 分钟 |
| 100 Gbps | 8 分钟 |

接收端只要不在“一个次代的时长”这么久的时间里失去联系，就一定能正确判断次代。现实中的
网络中断、乱序是秒级，所以 4 字节有一个以上的数量级余量；而回绕本身又必然换钥，
不会带来 nonce 重复。

帧头是定长的，好处是帧长算起来最简单：不开纠错时一帧就是“20 加明文长度”，等长批量
发送（GSO）、MTU 预算、解析和去重都保持最简单的形态，也不会出现同一个载荷在会话
早期能发、后期超 MTU 的情况；开纠错时数据片的帧长跟着包长走，冗余片的帧长是 20 加
`S`。

## 8. 参数与版本协商

### 8.1 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| 帧头 | 4 字节 | 固定宽度；计数器达到 2^32 时回绕并进入下一个次代 |
| `tag_len` | 16 | 可协商成 12（省 4 字节，留给伪造的概率是 2^-96）；客户端在握手请求里表达，网关定夺，会话内不变 |
| 纠错 `T` / `ds` | `T = 1`（整帧模式） | 开纠错时 `T` 取 2 / 4 / 8 / 16，`ds` 取 2 ~ `T − 1`；常用 16 / 12（12 片数据 + 4 片冗余）；两者握手时定下，会话内不变；走 TCP 时不开（可靠传输自带重传，见 §2.8） |
| 片长上限 | 1452 | `= 线缆 MTU(1500) − IP 头(20) − UDP 头(8) − 帧头(4) − tag_len`，`tag_len = 12` 时是 1456；开混淆时再减混淆层开销（见 §2.4、§2.6） |
| 内层 MTU | 1450 | 内层虚拟网卡的 MTU：网关上取配置值与片长上限中的小者，客户端拿到这个值后再按同一上限收一次（片长上限更小就以它为准），保证一个满长包一定放得进一片 |
| 组放弃超时 `T_group` | 1 秒 | 一组多久没有新包就放弃 |
| 组缓存时限 `T_group_recv` | 2 秒 | 接收端多久没动静就丢掉一组留的片 |
| 提前关组 `T_flush` | 关闭 | 开着时一组凑不满也会超时关掉（见 §2.4）；网关上用 `--early_close <毫秒>` 打开，取值 1 ~ 65535 |
| 保活间隔 | 60 秒 | 由网关的 `--keepalive` 配置决定；控制消息频率低，可以稍长 |
| `roam_cookie` | 8 字节 | 每个会话不同，握手下发，重新绑定后轮换（见 §4.1） |
| 凭证重叠期 | 10 秒 | 轮换之后旧凭证还能用多久，用来兜住轮换前发出的在途帧 |
| `cookie_beacon_K` | 64 | 每 K 帧附带一次 cookie；0 表示关闭 |
| `T_no_rx` | 1 秒 | 超过这么久没收到下行就补发漫游帧 |
| `hint` | 关闭 | 开启后握手查询是 O(1)，代价是静态公钥可被关联 |
| 压缩 | 关闭 | 握手参数 `0x0C`；两端配成同一个算法（deflate 或 lz4）才启用，只压压得动的 IP 包（见 §2.7） |
| 混淆 | 关闭 | 握手参数 `0x0D` + `0x13`；两端配同一个密钥串才启用，每包多 22~70 字节、内层 MTU 相应减小（见 §2.6） |

### 8.2 版本协商

握手里的版本字段用于协商协议版本。**收发双方必须先就版本取得一致，之后这个会话的
数据面只按该版本的格式解析**：不同版本的数据面格式彼此独立，同一会话里绝不混用。
版本只在握手时判定一次，之后不需要任何试探或探测。
